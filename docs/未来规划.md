## 六、AgentLoop 与 Workflow 并存设计（2026-08-22 补充）

### 6.1 需要解决的问题

当前系统把 AgentLoop 视为 Agent 的核心骨架，这对 ReAct 类型 Agent 是正确的：模型负责决定下一步，循环负责组织模型调用、工具调用、结果回填和终止判断。

但“Agent”是面向用户的能力单元，不等于某一种执行算法。以后可能出现以下类型：

- ReAct Agent：模型自主决定是否调用工具，适合开放式咨询、分析和探索。
- Workflow Agent：节点和边预先定义，按固定或条件分支执行，适合审批、报表生成、数据同步等确定性流程。
- 混合 Agent：Workflow 负责主流程，某个节点内部再调用 AgentLoop 完成开放式分析。

因此不能把“所有 Agent 都必须经过 AgentLoop”固化为全局架构约束。当前 AgentLoop 可以继续作为默认、最重要的执行引擎，但公共运行时应在它之上抽象出来，为其他执行引擎保留正式扩展位。

### 6.2 核心概念重新分层

```text
AgentDefinition（用户看到的一个 Agent）
        |
        +-- RuntimeProfile（公共能力与配置）
        |     会话、记忆、工具、模型、插件、事件、权限、预算
        |
        +-- ExecutionEngine（执行引擎）
              +-- AgentLoopEngine（ReAct 内循环）
              +-- WorkflowEngine（节点/边/状态机）
              +-- HybridEngine（未来，可嵌套调用其他引擎）
```

三者职责不同：

- `AgentDefinition` 描述“这是什么 Agent”，包括名称、类型、可用能力和入口配置。
- `RuntimeProfile` 描述“运行时能使用什么”，包括模型适配器、工具注册表、记忆方案、插件和安全策略。
- `ExecutionEngine` 描述“这次任务怎么推进”，决定步骤编排、状态转移、暂停恢复和最终完成条件。

换句话说，AgentLoop 不是整个 Agent，也不是所有 Agent 的唯一核心；它是 `ExecutionEngine` 的一个实现。当前版本只实现 `AgentLoopEngine`，但接口边界应按这个方向设计。

### 6.3 公共运行时与引擎边界

两类引擎都需要的能力放入公共运行时上下文，避免每个引擎重复实现：

- `ExecutionContext`：用户、会话、轮次、运行实例、追踪 ID、取消信号和截止时间。
- `ModelGateway`：模型调用入口；具体供应商由适配器或模型路由决定。
- `ToolRegistry`：工具发现、参数校验、执行和错误包装。
- `MemoryProvider`：加载历史、保存结果、上下文压缩或检索增强。
- `EventPublisher`：发布统一的运行事件，供轨迹、进度、监控和审计消费。
- `PluginRegistry`：注册事件插件、上下文贡献者、决策拦截器等扩展。
- `BudgetPolicy`：时间、模型调用次数、工具调用次数和 token 预算。
- `CheckpointStore`：保存可恢复的执行状态；Workflow 比 AgentLoop 更依赖该能力。

引擎只负责自己的编排逻辑：

- `AgentLoopEngine` 负责模型回合、工具调用、结果回填、重复调用保护和 ReAct 终止判断。
- `WorkflowEngine` 负责节点调度、条件分支、并行分支、重试、等待和状态持久化；它不应伪装成一次模型循环。

公共运行时可以调用引擎，但引擎不应直接依赖具体 Controller、数据库 Mapper 或某个前端页面状态。

### 6.4 建议的稳定接口

初步可抽象为以下契约，具体命名待实施阶段再定：

```java
public interface ExecutionEngine {

    String type();

    ExecutionResult execute(ExecutionContext context);
}
```

由 `EngineRegistry` 按 Agent 配方选择实现：

```text
agentKey -> engineType -> engine instance
general  -> agent_loop -> AgentLoopEngine
report   -> workflow  -> WorkflowEngine
```

这里的 `ExecutionResult` 不只包含最终文本，还应包含终态、错误信息、输出引用和恢复信息。执行过程通过 `EventPublisher` 发布，不能要求所有引擎都返回完整的内存事件列表。

`AgentRunService` 的职责也应逐步从“启动 AgentLoop”改为：

1. 根据会话和请求选择 `AgentDefinition`。
2. 捕获本次运行不可变的配置快照。
3. 创建统一的 `ExecutionContext` 和运行记录。
4. 从 `EngineRegistry` 选择执行引擎。
5. 提交引擎执行并处理统一的成功、失败、取消和恢复状态。

这样 Controller 和会话入口不需要知道当前 Agent 是循环还是工作流。

### 6.5 Workflow 的初版能力边界

Workflow 不应一开始就做成通用低代码平台。初版只需要支持可验证的最小模型：

- `workflow_definition`：版本化的节点和边定义。
- `workflow_run`：一次工作流执行及其状态。
- `workflow_node_run`：节点执行状态、输入输出、重试次数和错误信息。
- 节点类型先支持 `MODEL`、`TOOL`、`CONDITION`、`PARALLEL`、`END`。
- 节点状态至少支持 `PENDING`、`RUNNING`、`WAITING`、`SUCCESS`、`ERROR`、`CANCELLED`。
- 每个节点完成后保存 checkpoint，服务重启后可以从最近 checkpoint 恢复。

工作流节点应复用公共的模型、工具、记忆、事件和插件能力。例如 `MODEL` 节点可以调用一次模型，`TOOL` 节点可以调用注册工具；但它们不需要通过 AgentLoop 的“模型决定下一工具”流程。

### 6.6 AgentLoop 与 Workflow 的组合方式

推荐采用“引擎可嵌套”而不是复制能力：

```text
WorkflowEngine
  -> MODEL 节点
  -> TOOL 节点
  -> AGENT_LOOP 节点
       -> AgentLoopEngine
            -> 模型与工具循环
  -> CONDITION 节点
```

例如“先查询数据，再让 AgentLoop 分析，再生成固定格式报告”可以由 Workflow 编排；分析节点内部使用 AgentLoop。反过来，AgentLoop 也可以通过一个受控工具触发某个已注册 Workflow，但必须有权限、预算和递归深度限制，避免引擎无限互相调用。

### 6.7 数据与事件模型的调整方向

现有 `conversation`、`conversation_turn`、`conversation_node` 继续服务于用户会话和对话展示，不应强行承担所有工作流内部状态。

未来建议增加统一的运行维度：

- `execution` 或 `agent_run`：记录一次执行实例、采用的 Agent、引擎类型、配置版本、状态和预算。
- 事件表增加 `run_id`、`sequence_no`、`parent_node_id` 等字段，使事件既能按时间排序，也能表达并行节点和嵌套执行关系。
- Workflow 的节点执行记录单独保存，必要时通过 `run_id` 关联到统一事件流。

`agent_run` 的意义是“执行实例”，不是替代 `conversation` 或 `conversation_turn`：一个会话可以有多个 turn，一个 turn 通常对应一次主执行；复杂场景下一个主执行还可能包含多个子执行。把这些关系单独建模后，异步任务、重试、恢复、监控和嵌套引擎才有稳定归属。

本期不立即新增这些表。先保持当前 AgentLoop MVP 可用，在真正实现 Workflow 或需要可靠恢复前，再根据事件和状态需求定稿 schema。

### 6.8 插件与多引擎的关系

插件的核心思想仍然不变：宿主提供扩展点，执行到扩展点时调用已注册插件。但扩展点应按公共运行时和具体引擎分层：

- 公共扩展点：执行开始/结束、节点开始/结束、模型调用前后、工具调用前后、状态持久化前后。
- AgentLoop 扩展点：模型回合前后、工具调用决策、工具结果回填、循环终止判断。
- Workflow 扩展点：节点选择、条件判断、分支合并、等待恢复、节点重试。

因此插件可以声明自己依赖的能力范围。只订阅公共事件的插件可以同时服务两种引擎；只订阅 AgentLoop 事件的插件不会被错误地用于 Workflow。未来的“允许/阻止/要求确认/替换参数”等能力，应通过类型化决策扩展点实现，而不是让所有插件都返回一个万能上下文对象。

### 6.9 演进原则

1. 当前先把 AgentLoop MVP 做稳定，不能为了未来 Workflow 提前引入复杂工作流平台。
2. 新增抽象必须能解释清楚它解决的重复问题；暂不为了接口而接口。
3. 公共运行时只承载跨引擎稳定复用的能力，编排逻辑留在具体引擎内部。
4. Agent 配方选择执行引擎，Controller 不感知引擎实现。
5. Workflow 优先保证确定性、可观测、可恢复，再逐步增加动态能力。
6. AgentLoop 与 Workflow 可以组合，但必须限制递归深度、总预算和权限范围。

该设计把当前的 AgentLoop 保留下来，同时为“不是基于 AgentLoop 的 Agent”提供正式位置：不是再造一个特殊 Agent，而是注册一个新的 `ExecutionEngine`，由 AgentDefinition 选择它。

## 附录：dsh 插件机制三件套（阶段 1 的参考，2026-08-19 补充）

> 来源：深潜 DeepSeek Harness（dsh）插件机制后的笔记。先看"大白话版"，再看技术版。

### 大白话版（三句话）

1. **留槽位**：宿主先画好"接口/位置"（服务槽位），自己不写死"用哪个实现"。
2. **谁填都行**：插件实现这个接口，把自己注册进槽位；注册是"可逆"的——插件卸载，注册自动撤销。
3. **配置决定装哪些**：启动时按配置（profile → bundle → patch 分层）把插件一个个装进槽位；改配置 = 改拼装，甚至不用重启。

**agentLoop 为什么能换**：它只是"实现"，不是"代码里写死的那段循环"。宿主只认"谁实现了 AgentFactory 接口"——谁填槽谁干活；换实现 = 换填槽的人，宿主代码一行不用改。

### 技术版（三件套）

| 件 | dsh 对应物 | 说明 |
| --- | --- | --- |
| 服务槽位 | `Service` 基类，`super(ctx, 'key')` 注册成 `ctx.<key>` | 接口/注册表与实现分离；随所属 fiber 自动卸载 |
| 可逆注册 | `ctx.effect(execute, label)`，execute 返回 disposer | 卸载/热重载时逆序执行 disposer，注册自动撤销 |
| 配置树挂载 | `boot()` + cordis.yml + profile/bundle + cordis.patch.yml + `--patch` | 配置树 → Loader 挂载成插件树；patch 按 id 替换条目 config 或 insert |

### agentLoop 可替换的证据链（源码位置）

- 稳定契约：`packages/core/agent/src/index.ts` 的 `AgentRegistry extends Service`（注册为 `ctx.agents`），内部 `factory` 是槽位；`setFactory(factory): () => void` 返回 disposer 并注册进 effect
- 默认实现：`packages/core/agent-loop/src/index.ts` 的 `AgentLoop extends Service implements AgentFactory`，构造器里：
  - `super(ctx, 'agentLoop')` 注册自己
  - `ctx.effect(() => ctx.agents.setFactory(this), 'agentLoop.setFactory()')` —— "我是工厂"也是可逆副作用
- 关键约定（文档原文）：**扩展插件依赖 `agent`（接口），绝不直接依赖 `agent-loop`（实现），因此循环保持可替换**

### 对 Java 的翻译

| dsh | Java 等价物 |
| --- | --- |
| 服务槽位 `ctx.<key>` | 接口 + 服务注册表（Map / Spring Bean） |
| `super(ctx, name)` 注册 | 实现类启动时把自己注册进注册表 |
| `ctx.effect` 可逆副作用 | 注册返回 remove 函数，统一 try/finally 清理（Spring 用 @PreDestroy） |
| 配置树 + patch 分层 | 配置分层：默认 → profile → preset → 会话 → 覆盖（JSON/YAML patch） |
| 事件扩展点 | 类型化事件总线 + 拦截器链（waterfall = 责任链） |
| Loader 热重载 | 配置监听 + 注册表重建（先撤销全部，再重装） |

### 落地提示（阶段 1 用）

- 阶段 1 先做到"服务槽位 + 可逆注册"即可：工具注册表、LLM 适配器、事件日志三个 seam
- 配置分层和热重载放到阶段 2 再做，别一口吃成胖子
