# 后端功能模块化包结构

> 日期：2026-08-17

## 背景

AgentLoop、认证、会话和管理员监控陆续完成后，后端同时存在两种组织方式：Agent 核心按功能放在 `agent` 包中，其余 Controller、Service、Mapper、Entity 和 Repository 则集中在全局横向包。继续加入 RAG、Skill、文档解析和向量检索后，同一功能会散落到多个顶层目录，模块边界会越来越难识别。

## 设计决策

- 顶层优先按功能模块划分，当前模块为 `agent`、`auth`、`conversation`、`monitoring` 和 `common`。
- 模块内部继续使用熟悉的 `controller`、`service`、`dto`、`persistence` 分层，不引入过重的 DDD 模板。
- Entity、Mapper、Repository 跟随数据所属模块；Mapper 负责 SQL 与数据库映射，Repository 负责语义化数据访问、结果转换和持久化边界。
- 小模块不创建无实际内容的空包，随着类数量和职责增长再拆分。
- RAG、Skill 等属于未来业务能力，应成为独立功能模块；Milvus、Redis、DeepSeek 等属于技术实现，应放在所属模块内部。

## 本次迁移

- `auth`：认证 Controller、Service、DTO、Security，以及 `app_user` 的 Entity、Mapper、Repository。
- `conversation`：会话 Controller、Service、DTO，以及 Conversation、Turn 的持久化代码。
- `agent`：聊天 Controller、异步执行 Service、配置、Loop、Runtime、Memory、Tool、Event，以及 Node 持久化。
- `monitoring`：管理员监控 Controller、Service、DTO 和统计查询持久化。
- `common`：统一异常处理、健康检查和数据库启动迁移。
- Mapper XML 同步按 `agent/auth/conversation/monitoring/common` 分目录，`@MapperScan` 改为显式扫描各模块 Mapper 包。
- 删除没有调用方、与 `ModelAdapter + AgentLoop` 重复的早期 `ChatService`。

## 边界原则

Controller 只调用所属模块的 Service；业务代码不直接跨模块访问其他模块的 Mapper 或 Entity。当前 Agent 执行需要读写 Conversation 与 Turn，因此暂时依赖 Conversation Repository；后续只有在模块需要独立替换或测试隔离时，再抽取 Repository 接口，不为形式统一提前创建 `Impl` 类。

## 验证

- JDK 17 下重新编译全部 64 个 Java 源文件通过。
- Maven 测试通过，2 个工具测试无失败。
- 清理迁移前残留的旧 class 后，Spring Boot 在临时端口 `18080` 完整启动，五组 Mapper 包、Mapper XML、MyBatis-Plus 和 MySQL 连接初始化正常。
- `/api/ping` 返回 `200`，`/api/auth/csrf` 正常生成 Token，说明移动后的公共 Web、认证 Controller 和 Security 配置已生效。
- 包迁移后发现旧 Redis Session 中的 SecurityContext 仍引用原类名 `com.jam.agent.security.AuthenticatedUser`。Session namespace 升级为 `ai-agent:session:v2`，使不兼容旧 Session 自动失效；SecurityContext 改为仅保存在当前请求，后续 Redis Session 只保存用户 ID、用户名和管理员标记等稳定属性，避免再次因 Java 包名变化导致反序列化失败。
- 使用模拟旧 `JSESSIONID` 请求 `/api/auth/me` 返回预期的 `401`，不再产生 Redis 反序列化 `500`；健康检查仍返回 `200`。
- 退出登录不再直接 `invalidate()` Redis Session，避免 Spring Session 在请求提交阶段保存已失效对象而抛出 `Session was invalidated`。现在删除认证属性、清理 SecurityContext 并轮换 Session ID；登录成功时也主动轮换 Session ID，补齐自定义登录接口的 Session Fixation 防护。
- 管理监控页会并行请求总览和会话列表。SecurityContext 改为请求级后，Spring Security 曾将每次由自定义过滤器恢复的认证误判为新登录，并对同一 Session 并发执行自动 Session Fixation 处理，导致 GET 接口也出现 `Session was invalidated`。现关闭框架自动轮换，仅在真实登录成功时由 `AuthService` 主动 `changeSessionId()`。
- API 路径、数据库表结构和 AgentLoop 行为未做修改，本次为纯包结构与依赖引用重构。
