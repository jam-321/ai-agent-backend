# Token 预算与上下文压缩

- 日期：2026-08-23
- 分支：`feature/token-budget-compaction-backend` / `feature/token-budget-compaction-frontend`

## 背景

原有 `max-history-tokens` 只按历史字符数裁剪最近 Turn，没有统计 System Prompt、当前 Turn、Tool 定义和图片，也没有使用供应商返回的真实 usage。单个 Turn 内连续 Tool 调用仍可能撑爆上下文，管理员页面也无法观察模型调用成本。

本轮参考“点小数”的生产实践，把三个概念分开实现：上下文压缩负责单次请求能装下，Token 预算负责控制累计消耗，Round/Tool 上限负责防止循环失控。

## Token 记录与预算

- `ModelAdapter` 成为 LOOP、WORKFLOW、会话摘要和图片摘要的统一模型调用入口。
- 每次调用发布 `MODEL_CALL START/SUCCESS/ERROR` 事件，`conversation_node.content` 使用 JSON 保存 usage，不给通用 Node 表增加大量专用字段。
- 当前解析 `inputTokens`、`outputTokens`、`cachedInputTokens`、`cacheMissInputTokens`、`cacheWriteInputTokens`、`reasoningTokens`、`totalTokens`、返回模型、响应 ID 和耗时；供应商不返回 usage 时保留本地估算并标记来源。
- `TokenBudgetTracker` 在内存中同步累计一个 Turn 内跨 Attempt、Round 和 Workflow 步骤的真实消耗。预算判断不依赖异步监控写库。
- `magic_params.budget` 支持 `maxTokensPerTurn`、`maxContextTokens`、`maxOutputTokens`、`safetyMarginTokens` 和 `maxUserInputTokens`，值不能突破 YAML 全局上限。
- Chat Completions 的 `maxTokens` 和 Responses 的 `max_output_tokens` 使用当前 Agent 的有效输出上限。

## 两层上下文压缩

### 当前 Turn 上下文压缩

- 每次模型返回并完成工具结果回填后，估算下一次请求上下文；达到阈值后把较早消息交给模型生成结构化摘要。
- 压缩结果作为带 `[CONTEXT_SUMMARY]` 标记的首个 UserMessage，当前内存消息保留最近约 30000 Token，并保持 Assistant Tool Call/Tool Response 成对。
- `conversation_memory_summary` 保存当前 Turn 的最新上下文检查点；Turn 完成后补入最终回答，下一 Turn 和服务重启都从“检查点 + 后续原始消息”重建。
- 不再在 Turn 开始阶段额外调用摘要模型；Tool Result 的本地预览截断仍作为快速保护机制保留。
- 摘要模型失败时保留当前消息列表，只记录生命周期事件，不阻断当前用户 Turn。

### 默认预算

- 全局默认/上限：单 Turn 累计 2000000 Token，单次上下文目标 200000 Token，单次模型最大输出 8192 Token，单次用户文本输入 32000 Token。
- 上下文达到 160000 Token 时压缩，保留最近 30000 Token；历史重建兜底预算为 160000 Token。
- `memory.maxToolPairsPerTurn` 支持 Agent 级配置，控制每个历史 Turn 回填的工具调用对数量，默认值为 3。

### 内循环 Tool 结果压缩

- 新增 `conversation_node_output`，保存超大 Tool Result 的完整原文和估算 Token。
- 超过单条阈值时，模型上下文只回填预览、Turn ID、handle 和回查提示；新增 `query_tool_output` 支持 `offset/limit` 分页读取归档全文。
- 每个 AgentLoop Round 调模型前再次估算完整消息；多个中等 Tool Result 累计超限时，在内存中压缩已完成结果，但保持 Assistant Tool Call 与 Tool Response 成对。
- Tool 归档或压缩失败时回填原始结果，不能把一个成功 Tool 误判成失败。

## 管理员监控

- 监控总览增加模型调用、输入 Token、输出 Token、缓存 Token 和总 Token。
- 会话列表增加模型调用次数与 Token 总量。
- 会话执行树按 Turn 聚合 Token，并在每个 `MODEL_CALL` 节点突出显示输入、输出、缓存、推理和耗时。
- 聚合只读取 `MODEL_CALL/SUCCESS` 的合法 JSON；历史脏节点继续展示原文但不影响统计接口。

### DeepSeek 缓存统计修复

- Spring AI 1.1.7 的标准 Chat Completions usage 映射不会保留 DeepSeek 扩展字段，导致此前即使供应商返回缓存明细，Node 里也只有输入、输出和总 Token。
- `OPENAI_CHAT_COMPLETIONS` 改为直接解析原始响应 JSON，优先读取 DeepSeek 的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，同时兼容标准 OpenAI 的 `prompt_tokens_details.cached_tokens`、Responses 风格字段和 Anthropic 兼容中转字段。
- DeepSeek 缓存命中率统一按 `hit / (hit + miss)` 计算。缓存是供应商的尽力而为能力，系统只负责准确采集，不能保证每次请求必然命中。
- 管理员大盘、会话列表、会话详情、Turn 和单次模型调用均展示缓存命中率与命中/未命中 Token。
- 只有原始 usage 确实包含缓存命中字段的调用才参加缓存聚合；历史调用或不返回缓存字段的供应商显示“未上报”，与真实上报的 0 命中严格区分。
