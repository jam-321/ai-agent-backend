# 2026-08-22：工作流型 Agent 第一版

## 背景

当前所有 Agent 都固定走 `AgentRunWorker -> AttemptRunner -> AgentLoop`。AgentLoop 适合让模型自主决定工具调用和循环次数，但不能表达由系统预先规定步骤、分支和执行顺序的工作流 Agent。

本轮在不复制会话、短期记忆、事件流和终态持久化的前提下，为 Agent 增加第二种执行类型。

## 本次变更

- 新增 `agent_config.execution_type` 和 `execution_key`。
- 新增 `AgentExecutor`、`AgentRunResult` 和 `AgentExecutorRegistry`。
- 当前 `AttemptRunner` 接入 `LOOP` 执行器；新增 `WorkflowAgentExecutor` 处理 `WORKFLOW` 执行器。
- 新增 `com.jam.agent.workflow` 包，包含工作流定义、注册表、运行上下文和步骤处理器。
- 工作流第一版支持 `TOOL`、`MODEL`、`CONDITION` 和 `ANSWER` 步骤，以及成功/失败后继节点。
- 新增 `workflow_step_start/end` 事件，`NodeTracePlugin` 将其投影为 `WORKFLOW_STEP` 节点。
- 工作流复用 `ToolExecutor`、`ModelAdapter`、`ConversationContextManager`、`ProgressQueryService` 和 `TurnFinalizer`。
- 新增 `time_workflow -> time_report` 内置示例；已有数据库启动时会幂等补充该 Agent 配方。
- 新增 `magic_params.workflow.maxSteps`，并受 `agent.workflow.max-steps` 全局上限约束。

## 设计决策

- `workflow` 是独立功能模块，不把所有工作流类继续堆进 `agent` 包。
- AgentLoop 仍是 LOOP 类型 Agent 的核心骨架，但整个 Agent 系统通过执行器接口支持多种运行时。
- 第一版使用代码注册工作流定义，不引入 BPMN、数据库编辑器、可视化编排和工作流实例状态表。
- 工作流步骤中的工具调用仍必须经过 `ToolExecutor`，继续复用工具白名单、上下文注入、异常包装和工具轨迹。
- 工作流完成和失败统一由 `TurnFinalizer` 写入 assistant 终态和 `GENERATE` 节点，避免前端进度永久停留在运行中。
- 第一版不支持工作流中途断点恢复；涉及外部副作用的步骤应等幂等和补偿机制设计完成后再开放。

## 验证

- JDK 17 下执行 `mvn clean test`，13 个测试全部通过。
- JDK 17 下执行 `mvn -DskipTests package`，打包成功。
- Docker Desktop 启动后，MySQL 8.4 和 Redis 7 健康运行。
- 后端临时运行于 `18080`，前端临时运行于 `18081`。
- 注册并登录测试用户，调用 `/api/agents` 确认返回 `time_workflow`，再提交工作流聊天请求。
- HTTP 返回 `202`，进度最终为 `COMPLETE`；数据库中出现 `WORKFLOW_STEP`、`TOOL_CALL`、`GENERATE COMPLETE` 节点。
- 前端首页和 `/api` 代理返回 `200`，前端生产构建成功。
