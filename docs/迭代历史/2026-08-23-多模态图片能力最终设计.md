# 2026-08-23：多模态图片能力最终设计

## 设计状态

本文档是图片能力的最终初版设计稿，当前只完成方案确认和文档沉淀，尚未开始代码实现。

第一版目标是支持用户上传图片并让模型理解图片，同时兼容：

- AgentLoop 和 Workflow 两种执行流程
- 会话途中切换 Agent 和模型
- 支持图片的视觉模型与不支持图片的文本模型共存
- 图片原始文件持久化
- 图片历史的两种上下文策略
- 不破坏模型上下文前缀缓存

第一版不实现模型生成图片、音频、视频和 PDF 多模态输入。

## 一、核心决策

### 1. 图片是平台能力，不是普通 Agent 插件

图片能力涉及上传、存储、Turn 绑定、模型能力判断、历史重建和协议转换，因此属于平台基础能力。

AgentLoop 和 Workflow 共同使用统一的 Turn 输入：

```text
TurnInput
├── text
└── attachments
```

两种执行流程不分别实现图片逻辑，而是共同调用模型适配层。

图片压缩、OCR、审核、图片标签提取和特殊摘要策略，后续可以作为插件扩展。

### 2. 图片只在真正调用模型时转换为 Base64

数据库和内存上下文只保存图片引用及元数据，不保存 Base64。

模型调用前由 `ModelAdapter` 根据供应商协议临时读取 MinIO 图片并转换为：

- Base64 Data URL
- 预签名 URL
- 供应商 `file_id`

第一版只实现 Base64 Data URL。预签名 URL 和供应商 Files API 作为后续优化。

### 3. 图片历史支持两种模式

Agent 增加图片历史策略配置：

```text
image_history_mode
```

取值：

```text
FULL_IMAGE_HISTORY
SUMMARY_TOOL
```

默认使用 `SUMMARY_TOOL`；需要精细视觉回看能力的 Agent 可以配置为 `FULL_IMAGE_HISTORY`。

## 二、图片上传和存储

### 1. 前端交互

前端选择图片时只在浏览器本地预览，不立即上传。

用户必须输入文字后才能发送。发送时一次提交文字和图片：

```http
POST /api/chat
Content-Type: multipart/form-data
```

请求字段包括：

```text
message
conversationId
agentKey
modelProviderKey
modelName
images[]
```

后端和前端都禁止只发送图片的请求。

### 2. 对象存储

本地开发使用 Docker 中的 MinIO：

```text
MinIO API：127.0.0.1:9000
MinIO 控制台：127.0.0.1:9001
```

后端运行在 IDEA 时访问 `127.0.0.1:9000`；后端以后放入 Docker 时使用 Compose 网络中的 `minio:9000`。

图片桶设为私有。浏览器查看图片时通过后端鉴权接口读取，不提供永久公开 URL：

```http
GET /api/attachments/{id}/content
```

以后可以把 MinIO 替换为 AWS S3、阿里云 OSS 等 S3 兼容对象存储，业务层通过对象存储接口隔离具体实现。

### 3. MySQL 表

新增 `media_asset` 保存文件元数据：

```text
id
owner_id
asset_type                 IMAGE
storage_key
original_filename
content_type
file_size
sha256
width
height
status                     PENDING / BOUND / DELETED
created_at
deleted_at
```

新增 `conversation_turn_attachment` 建立图片和 Turn 的关系：

```text
id
conversation_id
turn_id
asset_id
sort_order
detail
created_at
```

`conversation_turn.content` 继续保存文本，不保存 Base64，也不把图片二进制放进 MySQL。

### 4. 图片生命周期

正常请求中，图片保存后绑定到当前 Turn。

异常情况下仍可能出现文件已经保存但 Turn 创建失败的残留，因此保留清理机制：

- `PENDING` 文件超过 24 小时自动清理
- `BOUND` 文件跟随会话保留
- 删除会话时先标记 `DELETED`
- 对象存储文件异步物理删除

## 三、模型能力和模型切换

图片能力按具体模型配置，而不是按供应商配置。

模型目录增加：

```json
{
  "modelName": "deepseek-v4-flash-vision-exp",
  "inputModalities": ["text", "image"],
  "supportsImageInput": true,
  "supportsTools": true
}
```

当前 DeepSeek 官方视觉模型使用：

```text
deepseek-v4-flash-vision-exp
```

普通 `deepseek-v4-flash` 不声明支持图片。

### 1. 当前 Turn 选择了不支持图片的模型

如果本次请求带有新图片，但模型不支持图片：

```text
返回 422
错误码：MODEL_IMAGE_UNSUPPORTED
不创建可执行 Turn
不自动切换模型
```

### 2. 历史中有图片，后来切换到文本模型

历史图片是否发送由 `image_history_mode` 决定：

- `FULL_IMAGE_HISTORY`：当前文本模型不支持图片时，移除历史图片本体
- `SUMMARY_TOOL`：不发送历史图片本体，模型可以调用摘要 Tool 获取文字摘要

无论哪种情况，都不删除 MinIO 文件和数据库附件关系。

模型配置在 Turn 开始时固定，运行中的 Turn 不受后续模型切换影响。

## 四、FULL_IMAGE_HISTORY 模式

### 1. 行为

重建历史时保留历史 UserMessage 的图片引用：

```text
历史 UserMessage
├── text
└── image attachment reference
```

模型请求前，`ModelAdapter` 读取这些图片并转换为 Base64。

### 2. 优点

- 模型可以重新观察原图
- 图片细节保留最完整
- 不需要额外摘要请求
- 不需要 `query_image_summary` Tool

### 3. 代价

- 历史图片可能在每次模型调用中重复发送
- AgentLoop 多轮工具调用会放大传输和视觉 token 成本
- 请求体更大，模型首 token 延迟可能增加
- 切换到文本模型后无法继续理解原图细节

如果图片消息和历史序列完全不变，供应商理论上可以复用前缀缓存，但是否缓存图片内容由供应商决定，不能保证。

## 五、SUMMARY_TOOL 模式

### 1. 异步生成图片摘要

包含图片的 Turn 主流程完成后，异步提交图片摘要任务：

```text
主 Turn 完成
    ↓
保存 user / assistant 终态
    ↓
异步摘要任务读取 MinIO 图片
    ↓
调用支持视觉的模型
    ↓
生成普通文本摘要
    ↓
写入 IMAGE_SUMMARY Node
```

摘要请求不属于 AgentLoop，不调用工具，也不影响主 Turn 的成功状态。

摘要模型只需要返回普通文本，例如：

```text
这是一张游戏战斗界面截图，包含玩家生命值、技能栏和敌人状态。
```

不要求摘要模型返回固定 JSON。

### 2. 摘要节点

在 `conversation_node` 中记录摘要任务：

```text
node_id: image-summary
node_name: 图片摘要
type: GENERATE
status: START / SUCCESS / ERROR
aggr_key: summaryJobId
content: 摘要文本或错误信息
```

需要增加图片关联字段，例如 `attachment_id`；如果一次摘要请求处理多张图片，则使用附件关联表或附件 ID 列表保存关系。

同一个摘要任务使用同一个 `aggr_key` 配对 START、SUCCESS 和 ERROR 状态。

### 3. 摘要生成失败

摘要失败不能影响主 Turn：

- assistant 正常回答仍然保存和返回
- Node 写入 ERROR
- `query_image_summary` 返回没有可用摘要
- 后续可以重试摘要任务

摘要异步生成时，下一轮可能先于摘要完成。Tool 查询需要支持：

```text
SUCCESS
PROCESSING
ERROR
NOT_FOUND
```

第一版 Tool 不在执行过程中再次嵌套模型调用；摘要尚未完成时返回 `PROCESSING`。

### 4. 图片摘要 Tool

新增：

```text
query_image_summary
```

Tool 自动限制为当前用户和当前会话，只查询 `IMAGE_SUMMARY` 且状态为 `SUCCESS` 的节点。

Tool 描述明确告诉模型：

```text
当用户询问历史图片、之前的截图或图片细节，而当前上下文没有图片本体时，调用此工具。普通文本问题不需要调用。
```

Tool 返回的 JSON 是后端 ToolResult 数据格式，不是要求摘要模型输出 JSON：

```json
{
  "items": [
    {
      "turnId": 3,
      "attachmentId": 101,
      "summary": "一张游戏战斗界面截图，玩家生命值约为 80%。"
    }
  ]
}
```

模型实际看到的消息仍然只是现有的：

```text
system
user
assistant
tool
```

### 5. 上下文缓存

摘要不会自动拼进 SystemMessage，也不会每轮生成 `a`、`ab`、`abc` 这种累计摘要。

只有模型主动调用 Tool 时，摘要才作为当前 Turn 的 ToolResponseMessage 进入上下文：

```text
AssistantMessage：调用 query_image_summary
ToolResponseMessage：返回图片摘要
AssistantMessage：基于摘要继续回答
```

这属于追加式上下文，不修改历史前缀，不会因为摘要集合持续变化而重写系统提示词或历史开头。

## 六、摘要和 JSON 的处理原则

正常回答不要求同时返回 answer 和 summary，也不强制正常模型输出 JSON。

如果未来需要独立摘要任务使用固定格式，只对摘要请求附加格式指令，并采用宽松校验：

- 摘要可以是普通文本
- 为空或超过限制时任务失败
- 格式异常不影响主回答
- 原始会话历史永远是权威数据
- 以后可以增加供应商原生结构化输出，但不是统一依赖

摘要内容视为不可信数据，Tool 返回时要明确标注为历史图片事实摘要，不应被模型当作新的系统指令执行。

## 七、缓存友好的上下文原则

当前 Agent 的稳定 SystemMessage、工具定义和已经完成的历史消息尽量保持不变。

禁止以下做法：

```text
每轮修改 SystemMessage 中的图片摘要
每轮在历史开头重写累计摘要
把所有历史图片 Base64 永久写入数据库
```

允许以下做法：

```text
当前 Turn 追加新的 UserMessage
当前 Turn 追加 ToolCall / ToolResponse
摘要作为独立 Node 保存
模型需要时通过 Tool 追加摘要结果
上下文接近上限时整体执行一次 compaction
```

## 八、对开源 Agent 的借鉴

### Codex

Codex 的核心原则是历史逐步构建，避免频繁重写上下文，并对注入内容设置大小上限。上下文接近限制时执行 compaction，将旧历史替换为 checkpoint，同时保留近期消息。

本地参考：

- `E:\ai\code\code2\codex-main\AGENTS.md`
- `E:\ai\code\code2\codex-main\codex-rs\core\src\compact.rs`
- `E:\ai\code\code2\codex-main\codex-rs\core\src\compact_remote.rs`

### Pi

Pi 使用 `CompactionEntry` 保存摘要和保留消息边界，摘要是普通文本 Markdown，不是强制 JSON。后续上下文由摘要和保留的消息组成。

本地参考：

- `E:\ai\code\code2\pi\packages\coding-agent\docs\compaction.md`

### DeepSeek Harness

DeepSeek Harness 的摘要请求复用原有 system、tools 和历史消息，把摘要指令追加在最后作为一次独立请求，以尽量复用前缀缓存。摘要使用固定 Markdown 结构和标签，不要求普通对话返回 JSON；成功后才写入 checkpoint。

本地参考：

- `E:\ai\code\code2\deepseek-harness\packages\compaction\compaction-basic\src\summarizer.ts`

### OpenClaw

OpenClaw 将摘要保存为 transcript 中的 compaction entry，保留近期消息；摘要失败时不修改原始历史。它支持可插拔的 compaction provider，但核心上下文压缩仍由宿主负责。

本地参考：

- `E:\ai\code\code2\openclaw\openclaw-main\docs\concepts\compaction.md`
- `E:\ai\code\code2\openclaw\openclaw-main\docs\reference\session-management-compaction.md`

Claude Code 没有公开完整源码，无法进行同等源码级确认；从外部行为看，采用的也是会话历史、上下文压缩和摘要 checkpoint 思路，而不是每轮修改动态 SystemMessage。

## 九、初版验收标准

1. 视觉模型可以接收文字和图片并正常回答。
2. 普通文本模型上传图片时返回 `MODEL_IMAGE_UNSUPPORTED`。
3. `FULL_IMAGE_HISTORY` 模式可以重建历史图片并发送给视觉模型。
4. `SUMMARY_TOOL` 模式在图片 Turn 完成后异步生成摘要 Node。
5. 模型需要时可以调用 `query_image_summary`。
6. 摘要生成失败不影响主 Turn 结果。
7. 切换到不支持图片的模型后，不发送历史图片本体，但可以查询历史摘要。
8. 数据库不保存图片 Base64，MinIO 保存原始图片。
9. 动态摘要不进入 SystemMessage，不重写历史开头。
10. 同一会话的历史图片权限严格按当前用户校验。
11. Workflow 和 AgentLoop 都可以接收统一的 `TurnInput.attachments`。
12. 删除会话后，图片元数据和 MinIO 文件最终可以清理。

## 十、默认配置

第一版默认：

```text
image_history_mode = SUMMARY_TOOL
单张图片最大大小 = 5 MB
单个 Turn 最大图片数 = 3
临时残留文件清理时间 = 24 小时
摘要 Node 最大内容长度 = 受控长度，超长截断或失败
```

需要精细回看图片的 Agent 可以改为：

```text
image_history_mode = FULL_IMAGE_HISTORY
```

以上设计只完成方案，不代表代码已经开始实现。后续只有在用户明确说“开始”后，才进入数据库、后端、前端和 MinIO 的代码改造。
